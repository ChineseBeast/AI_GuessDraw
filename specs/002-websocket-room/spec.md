# Feature Specification: WebSocket 房间管理系统

**Feature Branch**: `002-websocket-room`

**Created**: 2026-08-02

**Status**: Draft

**Input**: PRD 3.2 联机模式需求 MP-001 ~ MP-013，基于已完成的 Monorepo 脚手架（001）

## User Scenarios & Testing _(mandatory)_

### User Story 1 - 创建与加入房间 (Priority: P1) 🎯 MVP

玩家 A 打开联机模式，点击"创建房间"，系统自动生成一个 6 位邀请码。玩家 A 将邀请码分享给朋友。玩家 B 在联机页面输入邀请码，成功加入房间。房间内所有成员能看到实时更新的玩家列表。

**Why this priority**: 房间是联机模式的基础设施——没有房间就无法开始任何联机游戏。这是最核心的入口能力。

**Independent Test**: 可以完全独立测试：创建一个房间 → 用另一个客户端输入邀请码加入 → 确认双方都能看到对方在房间内。无需画布同步或猜词逻辑即可验证。

**Acceptance Scenarios**:

1. **Given** 用户已登录并进入联机模式页面，**When** 用户点击"创建房间"并选择配置（最大人数 4-8、难度），**Then** 系统创建房间并通过 WebSocket 返回房间信息和 6 位邀请码，用户进入等待大厅。
2. **Given** 房间已创建且处于 waiting 状态，**When** 另一用户输入正确的 6 位邀请码，**Then** 该用户加入房间，系统广播 "player_joined" 事件，所有成员看到更新后的玩家列表。
3. **Given** 房间已创建，**When** 某用户输入错误的邀请码，**Then** 系统返回"房间不存在或已失效"错误提示。
4. **Given** 房间已满（达到最大人数），**When** 新用户尝试加入，**Then** 系统返回"房间已满"错误。
5. **Given** 用户已在房间中，**When** 用户主动点击"离开房间"，**Then** 系统广播 "player_left" 事件，从房间移除该用户。

### User Story 2 - 实时画布同步 (Priority: P1)

当一名玩家在画布上绘画时，房间内所有其他玩家能够实时看到绘画过程——包括每一笔的起始点、路径、颜色、粗细和橡皮擦操作。同步延迟控制在 100ms 以内。

**Why this priority**: 实时画布同步是"你画我猜"联机体验的核心——如果看不到对方画画，联机模式就失去了意义。这是与房间管理同等优先级的基础能力。

**Independent Test**: 创建房间 → 两名玩家加入 → 一名玩家在画布上绘画 → 验证另一名玩家能实时看到相同的笔画。不需要猜词逻辑。

**Acceptance Scenarios**:

1. **Given** 两名玩家在同一房间且游戏已开始，**When** 绘画者在画布上绘制一笔（包含颜色、粗细、路径坐标），**Then** 系统通过 WebSocket 广播该笔画的完整数据，其他玩家在 100ms 内看到相同笔画。
2. **Given** 绘画进行中，**When** 绘画者使用橡皮擦擦除部分内容，**Then** 系统广播擦除操作，其他玩家画布同步擦除。
3. **Given** 绘画进行中，**When** 绘画者点击"撤销"，**Then** 系统广播撤销操作，其他玩家画布同步撤销最后一笔。
4. **Given** 绘画进行中，**When** 绘画者点击"清空画布"，**Then** 系统广播清空操作，所有玩家画布清空。
5. **Given** 网络延迟或丢包，**When** 某玩家收到的笔画数据乱序到达，**Then** 系统根据笔画序列号正确排序并渲染。

### User Story 3 - 回合管理与猜词 (Priority: P1)

游戏开始后，系统随机选择一名玩家作为"绘画者"，分配一个目标词汇，其他玩家在看不到词汇的情况下根据画作输入猜测。系统实时判断猜测是否正确，正确时给予提示并广播得分。一轮结束后自动切换到下一名绘画者。

**Why this priority**: 猜词是游戏的核心玩法闭环——没有猜词和计分，"你画我猜"就只是"画"。这是完成游戏体验的必需能力。

**Independent Test**: 创建 3 人房间 → 开始游戏 → 绘画者看到词汇并画画 → 其他玩家输入猜测 → 系统判断正确/错误 → 计分 → 回合切换。可以独立于排行榜、观战等高级功能测试。

**Acceptance Scenarios**:

1. **Given** 房间中有 3+ 玩家且房主点击"开始游戏"，**When** 游戏开始，**Then** 系统显示 3-2-1 倒计时，随机分配一名绘画者和目标词汇，绘画者看到词汇，其他玩家看到下划线提示（字符数）。
2. **Given** 某轮游戏中，**When** 非绘画玩家提交猜测文本，**Then** 系统判断是否正确：完全匹配则广播 "correct_guess" + 得分；部分相似则返回接近提示（如字数匹配）；完全不匹配则返回"再试试"。
3. **Given** 一轮游戏中，**When** 所有非绘画玩家都猜对或 60 秒倒计时结束，**Then** 系统结束当前轮次，展示正确答案、各玩家得分和绘画作品。
4. **Given** 当前轮次结束，**When** 系统切换到下一轮，**Then** 轮换绘画者（按顺序），分配新词汇，重新开始 60 秒倒计时。
5. **Given** 游戏进行了预设轮数（总轮数 = 玩家数 × 2），**When** 最后一轮结束，**Then** 系统展示最终排行榜，显示每位玩家的总分、最佳猜词和绘画作品集。

### User Story 4 - 断线处理与状态恢复 (Priority: P2)

联机游戏过程中，玩家可能因网络问题断开连接。系统应检测断线、给断线玩家一定时间窗口重新连接，并在重连后恢复其游戏状态。如果绘画者断线，系统自动分配新绘画者。

**Why this priority**: 断线处理提升用户体验韧性，但不是游戏的最小可用版本——在没有断线处理的情况下游戏仍可运行（虽然体验会差）。因此排在 P2。

**Independent Test**: 创建游戏 → 手动断掉一名玩家的网络 → 验证房间内出现断线提示 → 30 秒内恢复网络 → 验证该玩家状态恢复。可独立测试，不需要依赖排行榜等外围功能。

**Acceptance Scenarios**:

1. **Given** 某玩家在游戏中，**When** 该玩家的 WebSocket 连接断开，**Then** 系统在房间内广播 "player_disconnected" 事件，显示该玩家状态为"断线中"，开始 30 秒重连倒计时。
2. **Given** 玩家已断线且在 30 秒内，**When** 该玩家重新建立 WebSocket 连接并发送 "reconnect" 消息（携带之前的 session token），**Then** 系统恢复该玩家的游戏状态（角色、分数、当前轮次），广播 "player_reconnected" 事件。
3. **Given** 玩家断线超过 30 秒，**When** 重连倒计时结束，**Then** 系统将该玩家从房间移除，广播 "player_left" 事件。如果是绘画者断线，自动分配新绘画者并将计时器延长 10 秒。
4. **Given** 房主断线且超过 30 秒未重连，**When** 系统移除房主，**Then** 随机将房主权限转移给房间内剩余玩家中的一人，广播 "host_changed" 事件。

### User Story 5 - 观战模式 (Priority: P3)

玩家可以在游戏开始后加入房间作为观众，观看当前游戏进程但不能参与猜词和绘画。观众可以看到画布同步、当前分数和玩家列表。下一局游戏开始时，观众可以选择加入游戏。

**Why this priority**: 观战模式是社交传播的加分项（让朋友围观有趣的对局），但不影响游戏核心体验。作为锦上添花的功能排在 P3。

**Independent Test**: 创建 3 人游戏 → 游戏开始后第 4 人加入 → 验证第 4 人以观众身份进入，能看到画布但不能输入猜测 → 下一局开始时可选择加入游戏。

**Acceptance Scenarios**:

1. **Given** 房间中游戏已开始（状态为 playing），**When** 新用户通过邀请码加入，**Then** 该用户以观众身份进入，能看到实时画布、玩家列表和当前分数。
2. **Given** 用户是观众，**When** 当前对局结束、新对局开始前，**Then** 系统询问观众是否加入游戏，观众可选择加入成为正式玩家或继续观战。
3. **Given** 用户是观众，**When** 该用户尝试提交猜词或参与绘画，**Then** 系统忽略该操作，不报错但也不生效。

---

### Edge Cases

- 同一用户用多个标签页/设备加入同一房间 → 系统应拒绝，提示"已在房间中"
- 房间创建者离开后未转移房主 → 自动转移给加入时间最早的玩家
- 所有玩家都离开房间 → 房间在 5 分钟后自动销毁
- 邀请码碰撞 → 生成邀请码时检查唯一性，碰撞则重新生成
- 画布同步数据过大 → 对笔画数据进行压缩（如 Douglas-Peucker 简化路径点）
- 同一秒内多个玩家提交猜词 → 按服务器接收时间戳排序，先到先得
- 游戏过程中服务器重启 → WebSocket 连接全部断开，客户端应自动尝试重连
- 玩家在倒计时最后一秒提交猜词 → 以服务器收到时间为准，超过则不计分

## Requirements _(mandatory)_

### Functional Requirements

- **FR-001**: 系统 MUST 支持通过 WebSocket 协议创建房间，房间包含唯一 ID、6 位邀请码、最大人数、难度配置
- **FR-002**: 系统 MUST 支持通过邀请码加入房间，验证房间存在、未满、状态允许加入
- **FR-003**: 系统 MUST 在玩家加入/离开房间时广播事件给房间所有成员
- **FR-004**: 系统 MUST 将绘画者的画布操作（笔画、橡皮、撤销、清空）实时广播给房间所有非绘画者成员，延迟 < 100ms
- **FR-005**: 系统 MUST 为每条广播消息附加序列号，确保客户端可检测丢包和乱序
- **FR-006**: 系统 MUST 支持游戏流程状态机：waiting → countdown → playing → round_end → (next_round | game_end)
- **FR-007**: 系统 MUST 在游戏开始时随机分配绘画者顺序和目标词汇
- **FR-008**: 系统 MUST 实时校验猜词文本，正确时广播得分，部分匹配时返回接近度提示
- **FR-009**: 系统 MUST 按规则计分：首个猜对 15 分、第二个 10 分、第三个 5 分、绘画者每有一个猜对得 5 分
- **FR-010**: 系统 MUST 在每轮结束时展示正确答案、各玩家得分和画作
- **FR-011**: 系统 MUST 在游戏结束后展示最终排行榜
- **FR-012**: 系统 MUST 检测 WebSocket 断线，广播断线事件，提供 30 秒重连窗口
- **FR-013**: 系统 MUST 在断线玩家成功重连后恢复其完整游戏状态（角色、分数、轮次）
- **FR-014**: 系统 MUST 在绘画者断线超时后自动分配新绘画者并延长计时器 10 秒
- **FR-015**: 系统 MUST 在房主断线超时后自动转移房主权限
- **FR-016**: 系统 MUST 支持游戏开始后新加入者以观众身份进入
- **FR-017**: 系统 MUST 在观众尝试参与游戏操作时静默忽略
- **FR-018**: 系统 MUST 在空房间 5 分钟后自动清理销毁

### Key Entities

- **Room（房间）**: 唯一 ID、邀请码（6位字母数字）、房主 ID、状态（waiting/playing）、最大人数、难度、创建时间、玩家列表
- **Player（房间内玩家）**: 用户 ID、昵称、头像、角色（drawer/guesser/spectator）、分数、连接状态（connected/disconnected）、加入时间
- **GameSession（游戏会话）**: 关联房间 ID、当前轮次、总轮数、绘画者顺序、当前词汇、轮次历史
- **Round（轮次）**: 轮次序号、绘画者 ID、目标词汇、开始时间、猜词记录列表、状态（active/completed）
- **Guess（猜词记录）**: 玩家 ID、猜测文本、是否正确、提交时间、得分
- **CanvasStroke（画布操作）**: 序列号、操作类型（draw/erase/undo/clear）、笔画数据（颜色、粗细、坐标点数组）、时间戳

## Success Criteria _(mandatory)_

### Measurable Outcomes

- **SC-001**: 房间创建到 WebSocket 连接建立 < 500ms
- **SC-002**: 画布笔画从绘画者到其他玩家显示延迟 < 100ms（P95）
- **SC-003**: 系统支持 500+ 房间同时运行，每个房间 4-8 人
- **SC-004**: 猜词提交到判定结果返回 < 200ms
- **SC-005**: 断线重连恢复完整状态 < 3 秒
- **SC-006**: 空房间自动清理触发准确率 100%（5 分钟无活跃连接）

## Assumptions

- WebSocket 基础设施使用 Socket.IO（服务端 NestJS + @nestjs/websockets，客户端 socket.io-client）
- 房间状态存储在内存中（开发阶段），后续迁移到 Redis 以支持水平扩展
- 词汇库由服务端维护（从预定义词库随机选取），本 feature 使用静态词库
- 画布笔画数据格式复用 shared 包中已定义的 CanvasStroke 类型
- 用户认证基于 JWT，WebSocket 连接时通过 auth token 验证身份
- 服务端单实例部署（V1），多实例扩展在后续 feature 中处理
- 邀请码使用 6 位字母数字组合（排除易混淆字符 0/O/1/I/L），提供约 8 亿种组合
